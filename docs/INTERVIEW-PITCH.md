# 面试讲解稿

## 约 90 秒版本

这件作品解决的是中小企业采购流程散落在聊天、表格和 ERP 之间的问题：申请人不清楚谁在审批，审批人看不到统一金额口径，采购人员也很难确认 ERP 是否真正收到获批内容。

我把外围自动化和业务决策分开做了两条 n8n 工作流。第一条接收采购申请事件，校验字段后通过受限 API 建立申请，并用事件 ID 做幂等。第二条按工作日生成审批与 ERP 异常摘要，数据来自业务 API，邮件只进入本地 Mailpit。n8n 不审批，也不直接写 Odoo。

申请需要由部门负责人审批；超过演示金额门槛时，还要由不同财务人员复核。提交后供应商、商品、数量和价格被冻结。全部审批完成后，后台才根据已保存的审批版本在 Odoo 建立草稿采购单，再独立读回核对供应商、明细、币种和草稿状态。

最关键的异常是“请求超时，但 Odoo 可能已经创建成功”。系统把这种结果记为 UNKNOWN 并暂停自动创建；采购人员按稳定意图查询 Odoo，看到真实单据后再恢复核验，避免盲目生成第二张订单。整个演示使用独立的 Odoo 19、PostgreSQL、n8n 和 Mailpit 环境，不会确认采购单或执行付款。

## 追问时的展开

### 为什么需要两条 n8n 工作流？

接单和待办摘要属于两个不同触发点：一条响应外部事件并创建申请，另一条定期告诉岗位“现在需要处理什么”。它们都通过 API 访问业务，不共享数据库写权限，也不替代人工审批。

### 哪些步骤仍由人负责？

部门负责人判断业务必要性；高额申请由另一位财务人员复核；超出演示政策范围的申请先由管理员记录例外，再走完整审批；采购人员负责处理 ERP 的未知或错配结果并最终结案。系统约束角色和状态，不能靠隐藏按钮代替服务端鉴权。

### 为什么不在超时时直接重试？

超时只说明调用方没有收到确定响应，不能证明 Odoo 没有提交。系统因此复用同一个 ERP 意图标识先查 Odoo。查到并匹配时恢复为已核验；查不到时才允许采购人员对原意图显式重试；查询不可用时继续保持未知。

### 如何说明已验证范围？

可展示 `docs/TEST-EVIDENCE.md` 中的真实 Odoo 19 JSON-2 写入与读回、PostgreSQL 并发测试、浏览器审批流程、n8n webhook 和 Mailpit 邮件，以及受控的响应丢失恢复运行。真实企业节省工时、降低差错率和 Feishu 租户接入没有被测量或验证，因此不作这些声明。
